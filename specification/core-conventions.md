# Agent Docs Specification

LLM Powered AI coding agents are fantastic at writing code, but they need to read documentation to know how best to use 
libraries. Agents can normally get-by with larger and more well-known libraries (where lots of documentation 
is available), but struggle with smaller or less common libraries.

That is where "Agent Docs" come in … agent ready documentation for software libraries.

Because the author of this specification (and tools) is a Java veteran, and all my projects are Java-based. I 
have started with the conventions for Java. But there's no reason this could not be extended to other
languages and frameworks - if you want to help, get in touch!

## Agent Doc bundle conventions

Regardless of the language and build/binary frameworks used "agent docs" are essentially packaged 
[Agent Skills](https://code.claude.com/docs/en/skills). They follow the standard skill layout the only mandatory element
is a `SKILL.md` file.

- The `SKILL.md` - this is the root of your agent oriented markdown documentation for the library.   
  - **Note:**  Agent docs tooling will add YAML front matter so you do not HAVE to include this!
  - Agent docs tooling will pre-pend your description with language/framework specific instructions so an AI agent knows to which library the skill pertains.
    - If you have included a `description` in your front matter, it will be appended to that generated by the tooling.
    - The `name` field, will be overwritten/determined when the skill is actually used by downstream consumers of your
       agent docs. Safest thing is just to omit it!
- You can include more resources if you wish such as `references/`, `assets/`, and `scripts/` - following the agent 
  skills conventions.

## Client Consumption of Agent Docs bundle

Clients - that is software projects consuming a library that has an agent docs bundle - will extract the
bundle into an agent skill folder. 

The location and name of the skill root folder depends on the agent being used. (e.g. `.agents/skills`)

The name of the extracted agent doc skill is language/framework specific but it:
1. MUST be unique
2. SHOULD be short 
3. SHOULD be human-readable to the maximum extent possible (i.e. relate to the source library in some way)

The client will rewrite/create the `name` field in the 
`SKILL.md` front matter - so that the local agent has a short and relevant name for the skill that will associate in some
way with the library.

The client will prepend the `description` field in the `SKILL.md` front matter with language and framework specific 
instructions, so that the consuming agent can determine which library the skill is associated with.
